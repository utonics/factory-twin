# 03. 데이터 위임 — "데이터는 너가 임의로 발생하여 처리하자"

## 원문
> 데이터는 너가 임의로 발생하여 처리하자

## 상황
- 01·02번으로 애니메이션이 완성됨. Claude Code가 마지막 보고에서 "다음은 데이터 연결 방식을 정하거나 4~5단계로"라고 제안
- 실제 설비(PLC·MES)는 없음

## 의도
- 실데이터 대신 **가짜 데이터를 만들되, 실제 연동과 같은 구조로** 만들게 한다
- 구체 설계(어떤 센서·어떤 지표)는 AI에게 위임

## Claude Code가 한 일
1. 계획을 먼저 공유: 데이터 생성(가상 공장) → 처리(플랫폼) → 화면 반영 3단계
2. 차트를 그리기 전에 `dataviz` 스킬을 불러 차트 규칙(단일 계열, 임계치 기준선, 호버 툴팁)을 확인
3. 시뮬레이터에 **마모 모델**을 넣어 센서 값이 고장 전에 먼저 나빠지게 함
4. 가상 공장이 1초마다 센서 값과 설비 이벤트를 **MQTT식 토픽** 메시지로 발행 → 메시지 버스 → 처리기
5. 처리기: 시계열 버퍼, 알람(디바운스·히스테리시스·확인), OEE, 5분 단위 생산량, 불량 유형, 예지 보전(추세로 임계치 도달 예측)
6. 화면: OEE KPI, 알람 벨·알람 탭, 설비별 센서 차트, 라인 생산 차트, 장면 위 알람 표식
7. 측정 중 스스로 오류를 발견해 바로잡음
   - "고장 36건 모두 사전 알람"(100%)은 고장 알람 자체를 함께 센 측정 오류 → 측정 순서를 바꿔 다시 재니 43건 중 22건(약 51%)
   - 라인 OEE의 성능이 100%로 잘림 → 병목 설비 기준으로 계산 방식 변경

## 사람이 정한 것
| AI의 질문 또는 제안 | 사람의 결정 |
|---|---|
| (질문 없이 진행) 센서 종류·지표·처리 방식 | AI 설계 수용 |

## 검증
- 처리기 집계 = 시뮬레이터 실제 값(1라인 양품 961/961, 불량 33/33)을 테스트로 대조
- 테스트 15개 통과(알람 히스테리시스·디바운스, 추세 계산, 파이프라인), 타입 체크·빌드 통과
- 브라우저에서 센서 툴팁, 알람 발생 → 장면 표식 → 알람 탭 흐름 확인

## 방법론 포인트
- **짧은 위임 + 구조 기대.** 프롬프트는 한 줄이었지만, 01번에서 "나중에 데이터 연결"을 예고해 둔 덕분에 AI가 교체 가능한 구조로 만들었다
- **독립 대조.** 데이터 처리 결과는 "다른 경로로 센 값"과 맞춰 봐야 믿을 수 있다
- **100%는 의심한다.** 너무 좋은 결과는 측정 오류일 가능성부터 본다

## 교육용으로 다듬은 프롬프트
```text
Context: 실제 설비 데이터는 아직 없다. 나중에 MQTT 등으로 실데이터를 붙일 예정이다.
Goal: 설비별 가상 센서와 이벤트를 만들고, 이를 받아 OEE·알람·예지 보전 지표를 계산해 화면에 보여 준다.
Constraints: 처리기는 메시지만 보고 계산한다(시뮬레이터 내부를 직접 읽지 않음). 나중에 실데이터로 바꿀 때 처리기와 화면을 그대로 쓸 수 있어야 한다.
Output: 데이터 흐름 설명, 메시지 형식, 바꾼 파일 목록.
Verify: 처리기 집계가 시뮬레이터 실제 값과 일치하는지 테스트로 대조하고, 몇 시간 분량을 돌려 알람이 고장보다 먼저 뜨는 비율을 측정한다.
```
