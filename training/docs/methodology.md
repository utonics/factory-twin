# Claude Code 바이브 코딩 방법론 — FactoryTwin 프로젝트 기준

이 문서는 스마트 팩토리 디지털 트윈(FactoryTwin)을 만들면서 실제로 쓴 작업 방식을 단계로 정리한 것이다.
각 단계의 근거는 `../prompts/`의 프롬프트 기록(번호로 표시)과 전역 규칙 파일(CLAUDE.md)이다.
교육 자료의 뼈대이며, 팀 상황에 맞게 단계를 더하거나 고쳐 쓴다.

---

## 한 문장 정의

> **사람은 방향·범위·결정·승인을 맡고, Claude Code는 설계 제안·구현·검증·보고를 맡는다.**
> 그리고 둘 사이의 약속(완료 기준·커밋 규칙·정직한 보고)은 대화가 아니라 규칙 파일에 둔다.

## 한 번의 반복(루프)

```
사람: 프롬프트(방향 + 범위)
  → Claude Code: (해석이 갈리면) 질문
  → 사람: 결정
  → Claude Code: 구현 → 자체 검증(테스트·측정·브라우저) → 문제 발견 시 스스로 수정 → 보고(남긴 것 포함)
  → 사람: 결과 확인 → "커밋하고 main에 올려 줘"
  → Claude Code: diff 검토 → 커밋 → 푸시 → (배포) → 운영 재확인
```
이번 프로젝트는 이 루프를 6번(커밋 6개) 돌았다.

## 역할 분담

| 사람 | Claude Code |
|---|---|
| 무엇을 만들지, 이번에 어디까지 할지 정한다 | 템플릿을 도메인에 맞게 번역하고 설계를 제안한다 |
| 해석이 갈리는 결정을 내린다 | 결정이 필요한 지점을 찾아 질문한다(추천안 표시) |
| 결과를 보고 커밋·배포 시점을 정한다 | 구현하고, 테스트·측정·브라우저로 스스로 검증한다 |
| 계정 권한이 필요한 일을 한다(저장소 생성, 배포 연결) | 확인하지 못한 것은 "미검증"으로, 고치지 않은 것은 "남긴 것"으로 보고한다 |

## 단계별 정리

### 0. 준비 — 작업 공간과 규칙
- **작업 공간**: 작업마다 별도 브랜치·폴더(워크트리)에서 시작한다. 이번 작업은 Orca 워크트리의 작업 브랜치에서 했고, 원본 폴더의 `main`은 그대로 두었다.
- **규칙 파일(CLAUDE.md)**: 매번 말하지 않아도 지켜야 할 약속을 적어 둔다. 이번에 실제로 작동한 규칙:
  - 완료 게이트: 타입 체크 0 에러 → 빌드 성공 전에는 "완료"라 하지 않는다
  - 근본 원인 수정: 테스트를 건너뛰거나 주석 처리해 통과시키지 않는다
  - 범위 규율: 요청한 것만, 한 변경에 한 목적
  - git: 세션 시작 시 상태 확인, 커밋·푸시는 요청할 때만, Conventional Commits + 한국어 설명, 커밋 전 diff 검토
  - 정직한 보고: 근거 없는 수치 금지, 미검증이면 "미검증"
- **도구 연결(MCP)**: 브라우저 자동화(Playwright)를 연결해 두면 AI가 화면을 직접 띄워 검증한다.
- 함정: 규칙 없이 시작하면 "완료"의 기준이 매번 달라진다.

### 1. 마스터 프롬프트 — 로드맵 전체 + 이번 범위 (01)
- 전체 단계를 한 번에 보여 주되, 이번에 할 범위는 좁힌다("우선 … 애니메이션 구현부터").
- 남의 템플릿은 우리 도메인으로 번역해서 쓴다(창고·트럭·사이트 → 공장·AGV·구역).
- 프롬프트 5요소: Context · Goal · Constraints · Output · **Verify**. Verify를 넣으면 AI가 스스로 측정한다.
- 함정: 전체를 한 번에 구현하라고 하면 검증할 수 없는 크기의 결과가 나온다.

### 2. 진행 중 교정 (02)
- AI가 작업 중이어도 메시지를 보내 방향을 바로잡을 수 있다. 늦을수록 되돌리는 비용이 커진다.
- 참고 자료에는 "무엇을 참고하고 무엇은 따르지 말지"를 함께 준다("이미지 스타일만 참조하고").

### 3. 위임과 결정 분리 (03, 06)
- 세부 설계는 짧게 위임한다("데이터는 너가 임의로 발생하여 처리하자").
- 템플릿의 단계 번호만으로도 지시할 수 있다("원래 프롬프트 4단계 진행하자"). 1단계에서 로드맵을 줬기 때문이다.
- 작업량이 크게 달라지거나 되돌리기 어려운 결정은 AI가 시작 전에 묻게 한다(06: 구역 선택 해석, 테마).
- 함정: 위임했다고 결과를 안 보면, AI가 고른 기본값이 그대로 굳는다.

### 4. 자체 검증 루프 (01, 03, 06, 11, 16)
- 완료 게이트(테스트·타입 체크·빌드)는 최소 조건이다. 그것만으로 버그가 다 잡히지 않는다.
- **수치로 검증**: 몇 시간 분량을 돌려 통계·이상치를 본다(01: AGV-04 배터리 0%).
- **독립 대조**: 처리 결과를 다른 경로로 센 값과 맞춘다(03: 961/961).
- **너무 좋은 결과는 의심**: 100%는 측정 오류일 수 있다(03: 36/36 → 22/43).
- **기준치 → 수정 → 같은 방법으로 재측정**(11, 16).
- **A/B는 같은 입력에서만**: 지표가 나빠 보이면 비교 조건부터 본다(11: 난수 공유 착시).
- **실제 화면 확인**: 브라우저를 띄워 콘솔·캡처·클릭으로 본다(01, 06, 14).
- 함정: "테스트 통과" 보고만 받고 넘어가기.

### 5. 체크포인트 커밋 (04, 05, 07, 09, 15, 17)
- 동작하는 단계마다 사람이 "커밋하고 main에 올려 줘"로 체크포인트를 남긴다.
- AI는 커밋 전에 diff·시크릿·디버그 코드를 검토하고, 원격이 앞서 있으면 멈춘다.
- 외부에 영향이 있는 작업(게시·푸시·배포)은 AI가 먼저 묻는다(04: 공개 범위, 푸시 방식).
- 사람이 직접 칠 명령은 `!` 접두어로 같은 세션에서 실행해 결과를 대화에 남긴다.

### 6. 독립 점검 (08)
- 기능이 끝나면 "새 기능 금지"로 점검만 시킨다.
- 관점별 서브에이전트(로직 / 화면·성능)에게 병렬로 맡기고, 근거 없는 지적은 버리게 한다.
- 성능은 프로덕션 빌드로 잰다.
- 고치지 않고 남긴 것을 보고받아 다음 과제로 삼는다.

### 7. 설명 먼저 (10)
- 구조를 바꾸는 작업은 "어떻게 해결할건지 설명해 줘"로 시작한다.
- 원인(코드 위치) · 추천안과 대안 · 예상 효과(수치) · 바뀌는 파일 · 검증 계획을 받고 사람이 고른다.

### 8. 배포·운영 관찰 (12, 13, 14)
- "될까?"에는 근거와 "미검증" 표시를 함께 받는다(12).
- 사람만 아는 환경 정보(요금제, 연결 상태)는 짧게 알려 준다(13).
- 배포 후 운영 주소에서 다시 검증한다. 최신 코드가 배포됐는지 증거(번들 이름)로 확인한다(14).
- 원인을 못 찾으면 못 찾았다고 보고하게 하고, 판단 기준 자체가 틀렸는지 본다(14).

### 9. 마무리 (18)
- 백그라운드 작업 종료 · 임시 파일 삭제 · 브랜치/원격/배포 동기화 확인 · 남은 사항 기록.

## 이번 프로젝트에서 쓴 Claude Code 기능

| 기능 | 쓴 곳 | 효과 |
|---|---|---|
| 규칙 파일(CLAUDE.md) | 전 과정 | 완료 기준·커밋 규칙·정직한 보고를 매번 말하지 않음 |
| 질문(AskUserQuestion) | 06, 19 | 해석이 갈리는 결정을 시작 전에 확정 |
| 서브에이전트 | 08 | 관점별 병렬 코드 리뷰 |
| 스킬 | 03(dataviz), 19(utonics-lecture-deck) | 차트 규칙·사내 강의 표준을 절차대로 적용 |
| 브라우저 자동화(Playwright MCP) | 01, 03, 06, 08, 14, 16 | 화면 캡처·콘솔·FPS·클릭 검증 |
| 백그라운드 작업 | 개발 서버, 15·17 배포 대기 | 기다리는 동안 다른 일, 끝나면 이어서 검증 |
| `!` 명령 | 05, 07, 09 | 사람이 칠 명령을 세션 안에서 실행 |
| 워크트리 | 전 과정 | 원본 폴더의 main을 건드리지 않고 작업 |
| gh·Vercel CLI | 05, 13, 14 | 원격·배포 상태를 AI가 직접 확인 |

| 구조 변경 | "어떻게 해결할건지 설명해 줘" |

| 마무리 | "모두 종료하고 마무리하자" |
